# Semantic release review

Diego requested SemVer for his upcoming Vercel deployment and selected automatic
versioning from Conventional Commits. This change uses a pinned Release Please
Action, release pull requests and the built-in GitHub token. It adds no app
runtime dependency and does not deploy the local progress service.

## Independent review and resolutions

A read-only Claude session reviewed the diff with only Read/Glob/Grep available.
It did not run commands or edit files. Its report is reproduced below.

- Explicitly set `initial-version: "0.1.0"`. The version-pinned Release Please
  17.6.0 base strategy falls back to 1.0.0, confirming the bootstrap concern.
- Set `shell: bash` for CI dispatch, enabling pipefail so a failed JSON extraction
  cannot silently skip checks.
- Moved the version outside the home link and used screen-reader-only label text.
  The server layout passes only the version string to the client sidebar.
- Kept the initial changelog as a heading for Release Please to populate.
- Matched `@types/node` to Node 24 rather than allowing Node 26-only APIs in types.
  This replaces the previous dev dependency; it adds no runtime library.
- Resolve the command path before checking the version validator's CLI entry,
  so invoking it through a symlink still runs the guard.
- Removed the unsupported claim that Git tags are inherently immutable. Published
  tags should not be changed, but no tag ruleset is configured by this task.

The pinned v5.0.0 action SHA, its release-please dependency, output names and
`headBranchName` were checked against official source. The optional split of CI
permissions into another job is deferred: the current job contains the two
operations requiring the documented write scopes, with a pinned action and
read-only ordinary CI.

## Claude report

I found **one blocker**: as configured, the first release will most likely be `v1.0.0`, not `0.1.0`. There are three smaller fixes worth making and a few optional ones. Bootstrap, CI dispatch, permissions and the version check otherwise look right.

## Blocker

**1. The first release will probably be `1.0.0`** (`release-please-config.json:5-10`, `docs/RELEASING.md:52-53`, `CHANGELOG.md:4`)
- With an empty manifest and no previous release, Release Please uses its starting version. As far as I remember, that defaults to `1.0.0` unless you set `initial-version`. It does not read the current `package.json` version. I couldn't check the docs offline, so confirm in the linked `manifest-releaser.md`.
- `bump-minor-pre-major` doesn't help here because it only applies to versions already below 1.0.0.
- This will happen as soon as the branch merges. It contains `b08c117 feat: identify and validate application release versions`, which comes after `bootstrap-sha`. If that commit reaches `main` as a `feat:`, the first release PR opens right away.
- **Fix:** add `"initial-version": "0.1.0"` to the `"."` package block. Like `bootstrap-sha`, it only applies until the first release, and it records the intent either way.
- **Check:** the first release PR title should say `release 0.1.0`. If it says `1.0.0`, close it without merging. Fixing a published `v1.0.0` tag later is much harder.

## Should fix (not blocking)

**2. A CI dispatch failure can pass silently** (`.github/workflows/release.yml:36-40`)
- When a step has no `shell:`, GitHub runs it with `bash -e {0}`, which doesn't stop on a failure early in a pipeline. If `jq -e` fails, the `while` loop still exits 0, the step passes, and no CI runs on the release PR.
- **Fix:** add `shell: bash` to the step, which also turns on `pipefail`.

**3. Screen readers never hear the version** (`src/components/Sidebar.tsx:29,37`)
- The `<Link>` has `aria-label={text.sidebar.home}`, which replaces everything inside it, including the version.
- The `aria-label` on `<small>` is also not allowed on that kind of element, and screen readers ignore it. So the new `sidebar.version` strings in `messages.ts` are never used.
- **Fix:** move the version out of the link and drop the `aria-label`. Use the existing `.sr-only` class (`globals.css:77`):
  `<p className="app-version"><span className="sr-only">{text.sidebar.version} </span>v{version}</p>`

**4. The `CHANGELOG.md` intro text will probably be deleted** (`CHANGELOG.md:3-4`, medium confidence)
- As I recall, when the changelog has no version heading yet, Release Please rewrites the whole file as `# Changelog` plus the new entry. The two intro lines would disappear in the first release PR.
- **Fix:** either remove `CHANGELOG.md` from this change and let Release Please create it, or accept that the lines disappear.

## Optional improvements

5. **Narrower permissions** (`release.yml:18-22`): only the dispatch step needs `actions: write`. You could move it to its own job (`needs: release`, `permissions: { actions: write }`) and pass `prs_created` / `prs` through job outputs. That way the Release Please step never has it. The risk today is low because the action is pinned to a SHA.
6. **All of `package.json` may end up in browser JS** (`Sidebar.tsx:1,9`): `Sidebar` is `"use client"`. I haven't checked whether Turbopack drops the unused JSON fields. A clean fix is to import `version` in the server layout (`src/app/[locale]/layout.tsx:60`) and pass it to `Sidebar` as a prop.
7. **`@types/node` 26.6.4 vs Node 24** (`package.json:27`): the types allow Node 25/26 APIs that won't exist on CI or Vercel. Consider `@types/node@24.x`. That's a dependency change, so it's Diego's call.
8. **The version check can skip itself silently** (`scripts/check-release-version.mjs:23`): if the script path goes through a symlink, `process.argv[1]` won't match `fileURLToPath(import.meta.url)`. The script then exits 0 without checking anything. Splitting the command-line part from the validator, or comparing real paths, removes the risk. It's unlikely to happen on CI or Vercel.
9. **Docs wording** (`docs/RELEASING.md:5`): tags are not "immutable" by default. Either drop the word or enable a tag ruleset or GitHub's immutable releases setting.

## Checked and fine
- **Bootstrap SHA:** `bootstrap-sha` `e2aa3ef` matches both `main` and `origin/main`. It stays in history after a merge, so excluding old commits works.
- **Version table:** the examples match the config. `fix` gives 0.1.1, `feat` gives 0.2.0, `feat!` gives 0.2.0 while below 1.0, and `docs` alone doesn't release.
- **Action outputs:** in the v4 behaviour I know, `prs_created` is true when a PR is created **or updated**. Later pushes to `main` therefore re-run CI on the release branch, and `headBranchName` is the right field.
  - I couldn't verify the v5 SHA or its `action.yml` offline. Confirm that `prs_created` and `prs` still exist there. If they were renamed, the dispatch step would silently never run.
- **CI dispatch:** `workflow_dispatch` is GitHub's documented exception to "events from `GITHUB_TOKEN` don't start workflows", and it needs `actions: write`. Release branches are cut from `main`, so they get the trigger once this change merges. Passing the PR list through an env var avoids script injection.
- **Permissions:** the workflow default is read-only, and write access is limited to the release job. The scopes match the action's README.
- **Build check:** CI runs `npm run build` (`ci.yml:38`), so `prebuild` runs there and on Vercel. That holds as long as Vercel's build command stays `npm run build` and not `next build`. The Node release strategy updates the `package.json`, lockfile and manifest versions together, so the check passes on release PRs.
